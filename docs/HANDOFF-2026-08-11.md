## 1. BLOCKER — CI ingest truncates the dataset (1,596 → 96 repos)

> **Update 2026-08-12 — diagnosed and fixed. The hypothesis below was wrong.**
>
> It was **not** primary rate-limit exhaustion. The run's own logs show the
> budget was barely touched: `remaining=4891/5000` at the last success, with
> only 5 rate snapshots logged before successes stopped entirely.
>
> The actual cause: GitHub's **secondary** (abuse) rate limit, which answers
> `403` with a bare `{"message": …}` body and **no `errors` key**. `graphql()`
> checked only `json.errors`, so `json.data` came back `undefined`,
> `data?.repository` was falsy, and every throttled request was reported as
> *"repository not returned (private/deleted/renamed?)"* — indistinguishable
> from a deleted repo. Failures began at repo 86 and never recovered:
> 1,403 throttles + 99 `fetch failed` = 1,502.
>
> Why CI and not local: pacing. The 80 ms inter-request sleep plus a laptop's
> round-trip time kept local runs under the limit (~25 min for 1,598 repos).
> On a runner the round-trips are much quicker — the same loop completed
> 1,598 repos in 10 min, roughly 2.5× the request rate, which trips the
> secondary limit and then keeps re-tripping it.
>
> Fixed in `scripts/lib/github.mjs`, `scripts/ingest.mjs`,
> `scripts/check-dataset.mjs`, `scripts/reports/build_index.py`. See §7.

Run [31534706108](https://github.com/kaiser-data/github-stars-analyzer/actions/runs/31534706108)
got through the token gate, ingest, classify and precompute, then failed in the
reports step. The logs show why:

```
  <many lines>: repository not returned (private/deleted/renamed?)
  ⚙  Pre-computing graph for 96 repos…
     96 nodes · 286 edges · 8 communities
```

96 repos, not 1,596. Roughly 1,500 lookups returned nothing.

**Why it matters:** had the reports step not crashed, the job would have
committed a 96-repo `classified.json`, `graph.json` and snapshot to `main`,
Netlify would have redeployed, and the site would have lost 94% of its data.
The crash is currently the only thing protecting production.

**Leading hypothesis:** GraphQL rate-limit exhaustion mid-ingest, with per-repo
failures swallowed as "repository not returned" rather than aborting. Locally
the same ingest takes ~25 min and succeeds; CI finished in ~11 min, consistent
with most lookups failing fast rather than being fetched.

**Suggested fix, in order:**

1. **Make the pipeline fail loudly on a bad ingest.** Add a sanity gate after
   `classify` — if the repo count dropped more than ~10% versus the previous
   snapshot in `data/snapshots/`, exit non-zero *before* precompute and reports.
   A silent 94% loss should never be able to reach a commit.
2. Distinguish real 404s (deleted/renamed) from rate-limit/transport errors in
   `scripts/lib/github.mjs` — right now both print the same message.
3. Log the rate-limit headers (`x-ratelimit-remaining`, `x-ratelimit-reset`)
   during ingest so the next failure is diagnosable from the log alone.
4. Consider retry-with-backoff on 403/429 rather than dropping the repo.

## 2. Report generator crashes on an empty taxonomy

`scripts/reports/memory_frameworks.py:123`

```python
top_lang = sorted(langs.items(), key=lambda x: -x[1])
...
f"**{top_lang[0][0]}** ({top_lang[0][1]}/{len(present)} projects)."
```

`top_lang[0]` throws `IndexError` when `present` is empty — which is exactly
what happened when the truncated dataset contained none of its curated repos.

This is the only generator with this pattern (checked all 23), but the class of
bug is general: generators assume their curated repos exist. Worth a guard here,
and worth considering a shared helper that skips a report with a warning instead
of crashing the whole build when `present` is empty.

Note this is a *symptom* — with issue #1 fixed, it wouldn't have fired. Fix it
anyway so one bad report can't take down the other 22.

## 3. Credential hygiene — action required

- **A PAT was pasted into the chat transcript this session and must be revoked.**
  https://github.com/settings/tokens → find it → Delete. Treat it as compromised
  regardless of scopes.
- **Update 2026-08-28: the token in `.env` is dead** — it returns HTTP 401
  (`Bad credentials`). `GH_STARS_TOKEN` was set from that same token on
  2026-08-11 20:59 UTC, so **CI has failed at the token gate every Monday
  since**: runs `31998613913` (08-17, 19s) and `32694448840` (08-24, 23s) both
  die before `npm ci`. This is *not* the pacing fix failing — those runs never
  reach the ingest. The pacing fix remains unproven against live CI.

  Local refreshes work regardless by falling back to the `gh` CLI's own token:

  ```bash
  export GITHUB_TOKEN=$(gh auth token) && npm run refresh
  ```

- **It should be scopeless.** The workflow only reads public star data; `repo`
  grants read *and write* to all private repos. Regenerate with zero scopes at
  https://github.com/settings/tokens/new.

  **Do not set it via `pbpaste`.** Three attempts have now stored garbage —
  two on 2026-08-11, one on 2026-08-28 01:03 UTC — because the clipboard held
  the *command text* rather than the token. "Copy the token last" has failed
  every time it has been tried. Take the clipboard out of the loop:

  ```
  ! read -rs TOKEN && gh secret set GH_STARS_TOKEN --body "$TOKEN" && unset TOKEN
  ```

  Paste at the silent prompt and press enter. Nothing echoes, nothing lands in
  shell history, and the command text *cannot* be what gets stored, because the
  command is already running when you paste.

  **Verify before spending a CI run.** `gh secret list` only proves a secret
  exists, not that it is a token. Check shape and auth on the value first — a
  PAT is `ghp_` + 36 chars or `github_pat_` + ~80, and never contains a space:

  ```bash
  V=$(pbpaste)   # or however you hold it; this prints no secret material
  case "$V" in ghp_*|github_pat_*) echo "prefix ok";; *) echo "BAD PREFIX";; esac
  case "$V" in *\ *) echo "BAD: contains a space";; *) echo "no space";; esac
  curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: bearer $V" \
    -X POST -d '{"query":"{viewer{login}}"}' https://api.github.com/graphql
  ```

  A good token returns `200`. Only then dispatch a run — a bad secret fails at
  ~20-26s, a good one runs for minutes.
- Whatever expiry is set is the next silent failure date. Nothing alerts on a
  failed scheduled run; that is why this went unnoticed from 2026-08-03 to
  2026-08-11. Consider a failure notification on the workflow.
