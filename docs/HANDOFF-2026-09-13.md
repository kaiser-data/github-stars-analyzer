## 1. The prompt library — what it is

A report tells you *which* tools to use. It does not get you to a built thing. The
prompt library closes that gap: `stars → report → prompt → artifact`.

```
data/classified.json      ─┐
reports/<slug>.meta.json  ─┴→ scripts/prompts/<name>.py → prompts/<name>.md + .meta.json
                                                        → build_prompts.py
                                                          → public/prompts/index.json
                                                          → injects a cross-link into
                                                            reports/<parent>.md
```

Deliberately the same shape as `scripts/reports/`: a `GENERATORS` list, one generator
per artifact, a meta sidecar, an index the app reads, no API calls, reproducible.

### The generator contract

Each generator declares `SLUG`, `TITLE`, `REPORT` (parent slug), then:

| Field | What it is |
|---|---|
| `STACK` | `[(stage, repo)]` — resolved against `classified.json`, rendered with live metrics |
| `BRIEF` | **authored prose** — the thing the user pastes into a model |
| `INPUTS` | optional measured-inputs table, or `None` |
| `VERIFY` | shell commands, tools interpolated from `STACK` |
| `VARIANTS`, `VERIFY_HEADING`, `HEALTH_CAVEAT` | per-generator strings |

The split is the point: the shell is generated so it cannot go stale, the brief is
authored because no generator can invent it.

### Why it decays loudly

`STACK` entries resolve against the dataset at build time. A repo archived upstream
leaves the dataset (`sample.mjs` filters `!r.archived`), drops out of the table, prints
`WARNING missing:` and renders a banner in the prompt itself. A hand-written prompt
library silently recommends dead tools forever; this one complains.

**Drift is deliberately non-fatal**, matching `build_index.py`. One stale prompt must
not block 27 reports from rebuilding.

### Ordering is a correctness requirement

`build()` injects charts and copies each report to `public/reports/` **in the same
loop**. So cross-link injection must run *before* it. The sequence in
`build_index.py.__main__` is:

```
run_generators() → run_prompt_generators() → inject_cross_links()
                 → build() → build_prompts_index()
```

`tests/test_build_prompts.py::test_full_build_leaves_public_report_and_repo_report_identical`
is the regression guard. If it fails, the repo and published copies have diverged.

## 2. The thing no test can catch

`resolve_stack()` verifies a repo **exists**. It cannot verify the repo is **right**.

This bit us. `trading-dashboard` originally shipped `Kanaries/pygwalker` — which its own
parent report calls *"Exploration tool, not a production chart library"* — and picked
`echarts` (the report's #3 for financial charts) over `lightweight-charts` (its #1).
Every automated check passed: the repos existed, the table was well-formed, tests green.

**Choosing a stack is an editorial judgement against the parent report, every time.**
Before adding a prompt, read the parent report's "Which one should you use?" table and
justify any departure from it. There is no mechanical substitute.

Related rule, learned the same way: **if a brief names a tool, the user must be able to
install that tool from the stack.** The original brief said to use echarts *"via its
Python binding"* — `pyecharts`, a different repo, not in the stack. The fixed
`trading-dashboard` handles the JS/Python seam honestly: it says Lightweight Charts has
no official Python binding, tells you to write plain JS against the UMD bundle, and
bridges via `st.components.v1.html(...)`.

### Adding a prompt

1. Copy an existing generator in `scripts/prompts/`.
2. Pick `STACK` **from the parent report's recommendations** — see §2.
3. Write the `BRIEF`. It is the product; everything else is packaging.
4. Register it in `GENERATORS` in `build_prompts.py`.
5. `python3 scripts/reports/build_index.py` — expect `stack: N / N resolved`, no `WARNING`.
