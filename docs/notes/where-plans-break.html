Single-run census · 7 tasks · 15 agent reviews · 13 Sep 2026

What Each Gate Can See

Fourteen task-scoped reviews over 1.03M tokens found nothing important. One branch-scoped review costing a tenth as much found two merge blockers. Not because it was cheaper — because the defects that mattered did not exist inside any single task.

This page was wrong once already. Its first version claimed every defect was a plan defect and none were in the code — written after the 14 task reviews came back clean and before the whole-branch review ran. That review then found four Important findings, two of them merge blockers, several of them genuine code defects. The claim did not survive an hour. It is corrected below, and the correction is the more interesting result.

Also: n=1. One plan, one repository, one controller, one model family, no control arm. Seven tasks is not seven replicates. Nothing here is an effect size — it is a census of one run, with intervals so the width is visible.

01

What actually happened

A seven-task plan was executed by a fresh subagent per task, each followed by a reviewing subagent issuing separate spec-compliance and code-quality verdicts. Fourteen agent passes, 1.03M subagent tokens, 223 tool calls.

Every task passed review on the first attempt. No fix subagent was ever dispatched. The thirteen findings those reviewers raised were all Minor — style, consistency with sibling code, a Mac-specific label. Zero Critical, zero Important.

Then one reviewer read the whole branch at once, and returned do not merge.

It is tempting to read that as the task reviews having been sloppy. They were not. Re-read the two blockers and notice what they have in common: neither defect exists inside any single task's diff. Both are contradictions between artifacts.

BlockerThe contradictionWhich diff contains it
A A prompt recommends a tool its own parent report explicitly rejects — the report calls it “exploration, not production charting”, and ranks a different library first for exactly this use case. The feature's whole premise is that the prompt inherits the report's decision. Neither. The prompt is in one commit, the report was written months earlier and never changed. The contradiction lives in the gap.
B A new module raises on failure, and the raise sits upstream of the step that keeps two directories in sync — silently reintroducing a divergence that an existing file's docstring documents having already fixed once. Half in one commit, half in a file nobody's task asked them to read.

A task-scoped reviewer given that diff and that brief would be correct to approve both. The information needed to see the defect was not in front of them. This is not a quality problem; it is a scope problem, and no amount of rigour at the task gate fixes it.

The plan, separately, was wrong six times — and that part of the original finding survives. Each was caught by a different layer before becoming code.

02

The six

What matters is not that a plan had bugs. It is which kind. Not one was an algorithm error — the plan's logic was sound everywhere. Five of six were assertions about the surrounding codebase that nobody checked.

03

Known, and possibly not

Most of this is unsurprising. The part worth arguing about is narrower than the headline suggests, so here it is separated out.

Already well known

  • Plans written by an author with imperfect memory of a codebase contain errors.
  • Catching a defect earlier is cheaper than catching it later.
  • Review gates catch things; fresh context per task reduces confusion.
  • Cheap static checks are worth running before expensive dynamic ones.

The part that may be new

  • The defect class is lopsided. Zero logic errors; five of six were unverified claims about existing code. If that holds, plan review is the wrong activity — it should be a verification pass against the tree, not a coherence read.
  • The residue is convertible. One sentence in the dispatch — the real code is authority over the brief — is what turned defects 5 and 6 from build failures into reports. That clause is nearly free and did measurable work.
  • Review scope, not review rigour, set the ceiling. 14 task-scoped passes at 1.03M tokens: zero Important. One branch-scoped pass at 105k: four Important, two blocking. The cheap review did not win by being cheap — it won by being the only one allowed to see two artifacts at once.
  • Cross-artifact contradiction may be its own defect class, structurally invisible to per-task gates and not reducible to "review harder". Both blockers were of this class; neither was findable from the diff that contained them.
04

The claim, and how to kill it

Hypothesis 1 — scope sets the ceiling. Defects in agent-executed plans sort into two classes by the scope needed to see them. Task-scoped review, however rigorous, has a hard ceiling: it cannot find a contradiction between two artifacts when only one is in front of it. Adding more task-gate rigour trades against nothing; adding one branch-scoped pass changes what is findable at all.

Hypothesis 2 — plan defects are interface claims. Plan defects are dominated by unverified assertions about existing code rather than logic errors, and a mechanical pre-dispatch check — every import resolves, every signature matches, every filename satisfies the toolchain, every insertion point is valid — catches most of them cheaply. This one survived the correction intact.

Falsification. For H1: run plans under two arms, one with a branch-scoped pass and one without, and classify every escaped defect by the minimum scope needed to see it. If the escapes are mostly single-artifact, H1 is wrong and the task gate was simply sloppy. For H2: two arms with and without the pre-dispatch check, same plan author and model, counting whether the same defects arrive later as failed tasks.

What this run cannot tell you. Whether one branch-scoped pass is sufficient or merely better — this run has exactly one, found four Important findings with it, and has no way to know what a second reviewer would have found. The upper bound on what escaped is unmeasured, not zero.

The honest summary is narrow, and narrower than the version of this page that existed an hour ago. In one run: the plan was wrong six times in a way cheap checks caught; the code was wrong in ways only a reader holding two artifacts at once could catch; and the gate that found those cost a tenth of the gates that did not. Whether any of it generalises past this one plan, this one repository and this one model is exactly the open question — and the fact that the first draft of this page was confidently wrong about it is the best available evidence for treating single-run findings as hypotheses.

Method. One implementation plan, seven tasks, executed sequentially with a fresh implementer subagent per task and a separate reviewer per task issuing spec and quality verdicts. Controller held cross-task context and a durable progress ledger. Token and tool-call counts are the harness's own per-subagent figures, summed: 524,238 implementer + 503,125 reviewer = 1,027,363 tokens over 223 tool calls. Wilson score intervals at 95%.

Limits. Single run, no control arm, no replication. The plan author, the controller and the author of this page were the same agent — which plausibly inflates the pre-dispatch catch rate, and did produce one confidently wrong published claim, corrected above. The branch-scoped review was run on a more capable model than the task reviews, so model capability and review scope are confounded in this run and cannot be separated by it; that confound is the first thing a replication should break. Wall-clock durations are excluded because they include queueing. “Defect” means something that would have produced incorrect behaviour, a failed build, or a user-facing recommendation contradicting its own source — not a style finding.
